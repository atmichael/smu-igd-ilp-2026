# Implementation Plan: Document Evidence Storage

**Branch**: `002-document-evidence-storage` | **Date**: 2026-10-04 | **Spec**: [spec.md](spec.md)

**Input**: [Feature specification](spec.md)

## Summary

Build the server-owned durable evidence-storage service for AP review cases: retain original invoice, purchase-order, and receipt documents with their related structured records, preserve provenance and correction history, segregate invoice payable lines from PO commitments and receipt evidence, and maintain an immutable audit trail. Keep draft and final states distinct, enforce deduplication for final evidence, and ensure failed saves remain visible as failed or pending. This feature is intentionally limited to persistence, retrieval, provenance, and auditability; ingestion, extraction, classification, matching rules, and approval workflows remain separate responsibilities.

## Technical Context

**Language/Version**: C# / .NET 10 with ASP.NET Core minimal APIs and shared contracts; server-side persistence layer.

**Primary Dependencies**: ASP.NET Core, shared `ILP.Shared` models, repository-backed evidence store (object/file/DB abstraction to be selected in implementation), and the existing .NET test project.

**Storage**: Durable metadata store for evidence packages, source documents, structured records, provenance, and audit events; protected storage for original source documents and sensitive content; no raw invoice data or credentials in ordinary logs.

**Testing**: xUnit-style .NET integration tests under `tests/ILP.Server.Tests`, with persistence and retrieval contract validation for deduplication, provenance, and failure states.

**Target Platform**: ASP.NET Core backend service and shared contract layer, intended for the invoice-processing platform's server-side evidence domain.

**Project Type**: Full-stack backend service with shared data contracts; no front-end page or custom UI is included in this feature.

**Performance Goals**: Typical package retrieval under 10 seconds for normal AP review use; evidence package reads and writes must prioritize integrity and auditability over throughput.

**Constraints**: Preserve provenance without overwriting history; do not expose raw invoice content in ordinary logs; show failed save attempts as failed or pending, never success; keep drafts separate from final evidence; use stable identifiers for package, document, record, and audit linking; follow 3-year pilot retention default with production policy review before go-live.

**Scale/Scope**: Multiple source documents and structured records per AP case, with repeated review cycles and eventual archival, but no broad matching or payment decision logic inside this feature.

**Structure Decision**: Keep the evidence package feature in the backend and shared contract layers. The API layer will expose persistence and retrieval endpoints, the shared contract layer will define evidence models and statuses, and the server-side repository will own durable storage and audit retention. No client-specific state or workflow is included. The repository already contains the server and shared-model structure needed for this work, and the test project is the correct location for contract validation. To protect the current Gmail/camera intake workflow, the evidence layer will be additive: it will reference existing source-document IDs and intake metadata rather than redefining the current source-document DTOs as the durable evidence model.
