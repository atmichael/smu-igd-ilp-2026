# Implementation Plan: Scanned Document Upload

**Branch**: `003-scanned-document-upload` | **Date**: 2026-10-18 | **Spec**: [spec.md](spec.md)

**Input**: [Feature specification](spec.md)

## Summary

Add the user-facing upload workflow for one PDF, JPEG, or PNG file and finish the server side of the `file-upload` channel that already exists in the shared source-document intake. The React client runs quick checks (extension, 20 MB limit, not empty), submits through the shared intake with a retry-safe `Idempotency-Key`, and shows a confirmation with the source document ID, an "Upload another" action, and a view/download link for the original. The server gains a 20 MB limit for `file-upload` only, an explicit empty-file rejection, and recording of the sanitized original file name as display-only `origin.upload`. No new endpoint, storage path, or provider is introduced.

## Technical Context

**Language/Version**: TypeScript 6 / React 19; C# / .NET 10.

**Primary Dependencies**: Vite 8, MUI 9 (`@mui/material`), ASP.NET Core minimal APIs, PdfPig (already used for PDF page counting). No new packages.

**Storage**: The existing file-backed pilot stores: `IDocumentContentStore` for the original (`original.pdf` or `page-1.<ext>`) and `ISourceDocumentRepository` for the record. The record gains an optional `origin`. No new store.

**Testing**: Existing .NET integration tests in `tests/ILP.Server.Tests/SourceDocumentIntakeTests.cs`; Vitest and React Testing Library for client state and flows; manual browser matrix (see [quickstart.md](quickstart.md)).

**Target Platform**: Current stable Chrome, Edge, Firefox, and Safari on desktop; current stable Safari on iOS/iPadOS and Chrome on Android (FR-018).

**Project Type**: Full-stack web application (React client and ASP.NET Core API).

**Performance Goals**: No latency SLO. The upload shows in-progress state and the user can complete the flow in under one minute (SC-001).

**Constraints**: 20 MB (20 x 1024 x 1024 bytes) limit for `file-upload` only; camera capture and mailbox limits are unchanged. Server decides file type from content signature, never from the file name. The original file name is display-only, sanitized, never used in storage paths, and never logged. Reject before storing; store all or nothing.

**Scale/Scope**: One file per submission; one new client screen; one endpoint branch changed; one record field added.
