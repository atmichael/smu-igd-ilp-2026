# Implementation Plan: Camera Document Capture

**Branch**: `001-camera-capture` | **Date**: 2026-10-03 | **Spec**: [spec.md](spec.md)

**Input**: [Feature specification](spec.md)

## Summary

Build a mobile web camera-capture flow that requests camera access only after an explicit user action, captures and reviews up to three pages, and submits the accepted original images in order as one camera-sourced document. Use the browser Media Capture API for still frames and the existing React/TypeScript client; submit through a shared ASP.NET Core source-document intake contract. Do not duplicate durable evidence storage or downstream OCR work owned by adjacent features.

## Technical Context

**Language/Version**: TypeScript 6 / React 19; C# / .NET 10.

**Primary Dependencies**: Vite 8, browser `MediaDevices.getUserMedia`, ASP.NET Core minimal APIs, shared C# contracts. No camera library is required.

**Storage**: Captured `Blob` objects and preview URLs are held only for the active client session. On confirmation, originals are handed to the shared source-document intake and evidence-storage service; cancellation or exit clears local captures. Evidence storage is an explicit dependency on Feature 08.

**Testing**: Vitest and React Testing Library for client state and permission/capture flows; .NET integration tests for the intake contract; manual testing on current stable Safari on iOS/iPadOS and Chrome on Android.

**Target Platform**: Mobile phones and tablets using the supported browsers, plus the ASP.NET Core API. Camera access requires a secure browser context (HTTPS; localhost is permitted for same-device development).

**Project Type**: Full-stack web application (React client and ASP.NET Core API).

**Performance Goals**: No capture or upload latency SLO is specified. Keep at most three accepted pages per source document and return clear progress and recoverable errors during submission.

**Constraints**: Request video only, never audio. Acquire camera access after explicit user action. Stop all media tracks when leaving live capture, and release preview URLs on replacement, cancellation, submission, or unmount. The API validates media type, content, page count, and configured request size; never trust client filenames or log image contents. Do not persist unsubmitted images.

**Scale/Scope**: One active document per capture session; one to three ordered JPEG page images. No concurrency or throughput target is introduced by this feature.

**Structure Decision**: Keep browser permissions, stream lifetime, page ordering, preview, and cancellation in a focused React feature module. Expose a shared source-document intake endpoint from the ASP.NET Core API and keep cross-boundary metadata in `ILP.Shared`. The endpoint consumes the durable evidence-storage abstraction owned by Feature 08; it does not add a second storage implementation. Add focused client tests beside the feature and a server test project for the intake contract because no test projects currently exist.

**Dependencies**: Align the generic intake contract with scanned upload (Feature 01); use Feature 08 for durable original-page storage and provenance, Feature 17 for API authorization, and Feature 18 for request deduplication/retry guarantees. These are dependencies, not substitute implementations inside camera capture. If any dependency is not ready, keep the integration behind its contract and do not claim end-to-end persistence.
